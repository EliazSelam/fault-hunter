# Fault Hunter: context for a new session

## What this is
The public version of Eliaz's interactive learning system for electro-mechanical and optical machines ("מהרכיב למכונה"), from a resistor to AOI and AOS machines for PCB manufacturing. MIT licensed, published on GitHub Pages.

- Answer the user in Hebrew. UI text is Hebrew, technical terms in English. Repo docs and code comments are in English.
- Repo: https://github.com/EliazSelam/fault-hunter (public), branch `main`. Site: https://eliazselam.github.io/fault-hunter/
- **Public content only.** Nothing that identifies a specific employer, job opening or interview preparation, and no product names of a specific equipment maker. That material lives in a separate private repository and must not be copied here. Typical figures are described as "typical, from public manufacturer specifications".

## What the user expects
- **Teacher level, assume nothing.** Explain mechanisms, not labels. Every term a lesson uses is defined in that lesson.
- **Principles over memorization, interactive over text.** Prefer a simulation, a hint or a question to another paragraph.
- **Everything correct and validated.** A wrong number is worse than a missing one. Run the `fh-validate` skill (`.claude/skills/fh-validate/`) or `tests/run_all.sh` before any commit or publish, and quote the result.

## Architecture
- `src/` is concatenated by `build.sh`, in the order listed there, into one self-contained `index.html` (one `<script>`; all globals). A new file must be added to `build.sh`.
- Key globals: `COMPONENTS`, `SYSTEMS`, `SYSX`, `SCN` (51 faults), `QB` (147 questions), `QT` (question topics: every question's `t` must exist here), `VERIFY`, `LEX`, `PRINCIPLES` (12), `PRIN`, `go(sheet, arg)`.
- Some functions are reassigned in later files to add behaviour: `showS1`, `showSys`, `showInt`, `glossify`, `playScn`, `showQ`, `ansFig`. Read the later files before changing one.
- Hebrew and formulas: wrap text that contains formulas or units in `bidi()` (in `src/35-foundations.js`).
- Map of `src/`: 10–12 components (12 = repair laser and fiducials), 20 systems, faults in 30 + 38 + 39d + 50, questions in 39e + 39j + 50, 39i digital logic, 42 live figures (generated by `figures/embed.mjs` from `figures/*/build.mjs`; every figure needs a check in `tests/figures_audit.mjs`), 50 PCB/AOI/AOS tab and integration process, 51–55 from-zero lessons and lexicon, 56 motors tab, 57 machines and power conversion (extends the motors tab), 59 3D engine and simulations (view3, paint3; rotating field, backlash, scan head, laser crater, stepper), 66 process simulator (TOPICS: steps, quiz, fault trees, math; aoiScene), 65 navigation groups and site-wide search (wraps go, setTab, routeGo), 58 terms (definitions, TERM_LINK to the explaining page, the glossary tab, the inline pass), 60–63 lab and the 12 principles, 64 fault teaching layer.

## Topic rule
A topic in `src/66-topics.js` starts at the essence and widens: `punch` and `analogy`, then `steps` (3D, one lead element per step), `quiz`, `faults` (decision trees: every option leads to a node, leaves have `leaf`, `fix`, `pr`, optional `go`), and `math` (MathML via the `MM` helpers, numbers added to `VERIFY`). `tests/topics_audit.mjs` walks every leaf.

## Zoom
`src/77-zoom.js` (tab `zoom`, first under "getting started") is the system zoom, like "Powers of Ten": five scales (1 components, 2 small circuits, 3 mechanisms and principles, 4 systems working in parallel, 5 the process), each made of the one below. `ZOOM` lists the nodes; a node has a core window and windows around it, and `parts` (zoom in; the parents are derived for zoom out). A window is a unit that already exists in the project (lesson part via `zParts`, `formBox`, `bench`, a system bench, a live figure, a 3D sim, a topic scene, flow, derivation, fault tree, quiz, an atlas card, a motor window captured once by `zCapture`). Every window has exactly one home; several windows on one subject at different depths are fine, the same content twice is a duplicate. `tests/zoom_audit.mjs` checks homes, rendering, duplicate content, structure, navigation and authorship.

## The machine in 3D (main layer)
`src/79-machine3d.js`: the zoom tab opens on one complete inspection machine in 3D (`MPARTS`: each part is boxes, an explode direction and a zoom node). It assembles itself on open, explodes with a slider, turns, zooms, and a click flies to a part and lists its windows in two layers: layer 1 shows and simulates (`LAYER1` kinds), layer 2 explains. Node pages show layer 1 before layer 2. `INNER` (keyed by topic) holds inner assemblies: opening a part explodes it into the parts it is made of, recursively (`mOpen`, `mUp`, `MS.path`); every inner part must be the topic itself or a part of it in the zoom tree, and the zoom suite checks it. `ZAPPX` holds the topics that are not parts of the machine (production line, digital logic, measurement); they are appendices, not parts of anything.

## How the zoom tab is put together (stage 2, done in v2.35.0)
Nothing in the zoom tab wraps or reassigns another function; to add something, register it. Plan and notes: `docs/STAGE2_PLAN.md`.
- **Window kinds** (`WIN` in `77-zoom.js`): `WIN.add({ id, test, info, mount, ctx })`. Later registrations are checked first; `base` answers the rest. `zInfo`, `zMount`, `zWinCtx` are plain delegates. `WIN.mount` always returns an **activity handle** (`getState/setState/pause/resume/destroy`, also `el.act`); a kind may return its own (animations do), otherwise one is built from the step buttons, the controls and the 3D cameras (`cv._V`, set by `view3`).
- **Views** (`ZVIEW`): `ZVIEW.add(id, { group: 'main' | 'back', order, title, bar, render })`; the views bar is built from it. `showZoom(arg)` only parses the route.
- **Topic page** (`NODE_SECTIONS`, `nodeSection(id, order, { html, wire })`): visit, path, crumb, title, hub, children. **Machine side panel** (`MSIDE`, `msideSection(id, order, modes, { html, wire })`; modes whole, part, inner, line). **Machine bar** (`MBAR_TOOLS`): the machine switch and the finder. **Hooks:** `MHOOK` (before/after selecting a part, after switching machine), `GO_BEFORE` (before the page is replaced; declared in 77 because the build loads 40-app last).
- **Links and history** (`86-links.js`): `#/zoom/<node>/<hub>/<window>`, `#/zoom/machine?m=&sel=`; a new topic or view pushes, a hub or window change replaces; window snapshots live in `HS.snap` and `sessionStorage`.
- **Outside this rule:** the shell's `go`/`setTab`/`routeGo` wrappers (65, 72) and the legacy simulator tab's wrappers (70) are untouched.

## The machine in real-time 3D (v2.39)
`src/91-machine-gl.js`: `FH3D.machine(THREE, cv, V)` is only the picture of the machine view. `zMachineView` (79) still owns the logic, the projection (`view3`), picking (`MS.polys` from the boxes of `MPARTS`), names and pointer; when `MS.gl` exists it skips its own painting and calls `MS.gl.render()` after `draw()`. The WebGL canvas (`.mgl`) sits under `#mc` (`.mtop`) and `aim()` reproduces `view3`'s projection exactly (checked: under half a pixel). `PB[id]` builds each part inside its boxes (default: rounded boxes); `buildInner` draws `INNER` parts by name. `fh3dKit(THREE)` in 90 is the shared kit. Software-only WebGL (detected by renderer name; headless test browsers are that) returns null and the earlier drawing stays, unless `FH3D.software = true` (the suite sets it for the 3D checks only). `GO_BEFORE` frees the context.

## One renderer (v2.41)
`fh3dCore(THREE)` in `91-machine-gl.js` is a singleton: renderer, studio, lights, floor, materials, `PB`, `innerPart`, `aim`, `project`, `attach(cv, cls)`/`fit(cv)`/`release(mark, cv)`. A view (`fh3dMachine`, `fh3dObject`) attaches the one canvas under its own 2D canvas, adds its groups to `core.root`, sets `core.owner`, and on destroy removes its groups and releases everything it created after its mark. `attach` destroys the previous owner. `fh3dObject(THREE, cv, V, id)` mirrors `hubGeometry` (kinds inner, part, one, machine) and is created in `hubObject` (84) as `HS.gl`. The scan head window keeps its own renderer.

## Inner parts as components (v2.42)
In `fh3dCore`: `IL` is a library of small models (coil, relay, mosfet, cap, transformer, pcb, lens, …), `IRULES` maps a part's Hebrew name to one (first match wins; order matters), `innerKind(t)` answers which. A model is built in a local frame laid into the part's box (`fThin`: z is the thin side; `fLong`: x is the long side; `fUp`: z is up), in fractions of the box, so it fits any orientation. `innerPart` uses the model, or the plain rounded body if no rule matches. The zoom suite fails if any `INNER` part has no model or if a model leaves its box (`MS.gl.innerFit()`). A new inner part: give it a name an existing rule matches, or add a model and a rule.

## The machine at work (v2.40)
Also in `91-machine-gl.js`: `MS.gl.run(true)` plays one cycle (`timeline(kind)`: a list of `[seconds, step(k), status]`), `runSeek(t)` puts it at a time (the checks use it), `runPlan()` reports the swath, pass time and targets. `RUNC` derives the swath from `scanCalc(1200, 0.5, 5)` and the repair targets from `AOISCAN.removal`. Moving parts get offsets in `RUN.off` (camera, lens, strobe or laser, reg along x; table and panel along y); the overlay canvas rides the panel group. It never starts by itself. In the line view (`kind === 'line'`) the timeline is `scanSteps` + carry + verify + carry + `repairSteps`; `RUN.stage` (scan, carry, verify, carry2, repair) drives the overlay and labels, `RUN.pan` is the travelling panel's offset (the AOI copy's panel; offsets are keyed `m:id`, and `RUN.hide` hides the AOS copy's panel), and `seek` steers `MS.Ct` so the view follows the panel. Known limit of the model's geometry: table travel is about 1.6 units for a 2.4-unit panel, so the cycle covers a coupon, not the whole panel; a full-panel scan needs a longer base in `MPARTS`.

## The book as a textbook (v2.59)
A chapter is the lesson and is read whole without leaving it. `bookChapter` (95): `bookRecap` (what the chapter needs, inline), why and goals, then each topic by `bookTopicHtml`: the eight levels `BK_LV` (MASTER's), a window's level from its kind (`BK_KLV`, `bookWinLv`), an asset's from MASTER; the main windows open (`data-auto`), every other window and every asset of the topic one press away in place (`bookWin`, `bookEmbItem`; `bookMount`/`bookUnmount`, one heavy item at a time in `BKL`). `bookLayout(c)` places the assets: a bank question goes to the exercises (the first of a topic with steps becomes its solved example, `bookWorkedHtml`), a fault to the chapter's faults, a simulation that is a window stays the window, a page that is a window takes its place at the asset's level; the rest to its topic or to "more in this chapter". `bookChecks` adds the intuition questions (an answer written first, `.bk-nb`) and the calculation: a solved example with fixed numbers (`bqExample` in 96) and the try-it (`bqMount`). `bookEndHtml`: summary, formula sheet, exercises and their answers (`.bk-key` opens only after an answer is written; `bookKeyFill`), my questions (`bookMyqRender`), the faults. `bookIndexHtml` reads the drawn chapter for its index. `BKID` gives every item an id for one drawing. `bookFrameHtml` (97) is now only the certification, its faults jumps to the embedded faults; `bookReqRefresh` redraws it when progress changes in a frame. ## Continuity rules
Arrow keys belong to an activity when the focus is in it; the page's level navigation answers only from the page or its navigation (`81-polish.js`). A hub window's state (step, controls, animation step and parameters) is saved before it is replaced or the topic is left, and restored when it opens again (`winSave`/`winRestore` in `84-hub.js`). Animations run on a simulation clock that pause freezes. The topic object is still during an activity and turns only under the pointer or with the focus; it is a keyboard button with a visible button beside it. Visits are called visits ("ביקרת"), not understanding. Each finding from the external review (F01–F06, F08, F10) has its own behaviour check in the zoom suite.

## Structure rule
Every topic has an `ARCH` entry in `src/70-structure.js`: `why`, `f3` (CEO, architect, engineer), `blocks` (int, if = interface, ext = other system, with x, y), `flows` (from, to, signal kind e/d/m/o/p, label, the steps where it is active), and `rev` (for every block: what breaks, the first failing step, and an optional simulation preset). ## Learning model rule
Every topic follows the levels in `src/67-topic-levels.js`: map (where in the machine), essence (steps with `pred` predictions), intuition (`quiz`), engineering depth (`explain` self-explanation), faults (each with `solo` observations and its answer leaf, shown worked, guided and on your own), math (optional), integration (`integ`, linking other topics), and review. Each of see, eng and math ends with a `checks` question. Answers feed a Leitner review queue in localStorage (1, 3, 7, 21 days), interleaved across topics.

## Terms rule
Every new English term must be defined (in `TERM_NEW` in `src/58-terms.js`, or in `LEX`), and given a `TERM_LINK` to the page that explains it if there is one. `tests/terms_audit.mjs` fails on any undefined term. English sentences (interview lines, machine messages) get `lang="en"` so they are not glossed.
